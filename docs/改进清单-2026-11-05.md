### M2. 私有上传图片可绕过鉴权（已实测复现）
- **问题**：`public` 静态托管只对「路径字面以 `/uploads/` 开头」的请求让路，编码斜杠、双斜杠等变体不匹配，于是落到静态中间件，直接返回原图。
- **证据**：
  - `agriculture-backend/app.js:87-91`：
    ```js
    const staticHandler = express.static(path.join(__dirname, 'public'), { index: false })
    app.use((req, res, next) => {
      if (req.path.indexOf('/uploads/') === 0) return next()   // 交给后面的鉴权路由
      return staticHandler(req, res, next)
    })
    ```
  - 鉴权路由在 `app.js:256-309`，只覆盖正常路径。
  - 实测（未携带任何 token，直接 GET）：
    - `/uploads/<私有历史图>` → **401**；
    - `//uploads/<同一文件>` → **200**，4,929,143 字节，`image/png`；
    - `/uploads%2F<同一文件>` → **200**，同上。
- **影响**：只要拿到文件名（分享链接、日志、旧 URL 都可能带），任何人都能读别人的作物照片；与 `app.js:297-302` 写的「识别记录属于个人隐私，不公开」直接矛盾。
- **建议改法**：在静态包装中间件里先做规范化再判断：`decodeURIComponent(req.path)` 后折叠重复斜杠、拒绝 `..`、统一小写盘符后判断 `/uploads/`；更稳的是让静态中间件明确排除整个 `public/uploads` 目录（例如把 uploads 移出 `public`，只由鉴权路由 `sendFile`）。加自动化用例覆盖 `//uploads`、`%2F`、`%2e%2e`。
- **改动量**：约 10~15 行、1 个文件 + 1 条测试，约 0.5 天。

- **问题**：为了给 `<image>` 带鉴权，前端把 token 拼到 `/uploads/...?token=`；后端所有鉴权路由都接受 `req.query.token`；访问日志记录完整 URL，导致 token 落盘。
- **证据**：

  - `utils/config.js:160-166`：`withToken()` 给所有 `/uploads/` 拼 `token=`；

- **改动量**：约 10~15 行、2 个文件，约 0.3 天。

### M9. `POST /api/_restart` 在反向代理后会变成「公网可重启」
- **问题**：该端点只靠 `req.ip`/`remoteAddress` 是否为本机来判断；项目未设置 `trust proxy`。按文档建议用 nginx/HTTPS 部署后，所有外部请求在 Node 看来都来自 127.0.0.1。
- **证据**：
  - `app.js:231-238`：`const ip = String(req.ip || req.connection.remoteAddress || '').replace('::ffff:', '')`，只允许 `127.0.0.1/::1/localhost`；
  - 全仓库没有 `app.set('trust proxy', ...)`（`grep` 无结果）；`docs/开发文档.md:808` 也写明「helmet 安全头 / trust proxy ❌ 未启用」。
- **影响**：公网用户可通过代理访问 `POST /api/_restart` 把服务停掉（进程退出），造成 DoS；若 PM2 自动拉起，至少造成服务抖动。
- **建议改法**：生产环境直接不注册该端点（`NODE_ENV === 'production'` 时 404），或要求管理员 session + 独立密钥；如确需保留，显式设置 `trust proxy` 并把判断改成 `req.socket.remoteAddress`。
- **改动量**：3~5 行、1 个文件，约 0.1 天。

## 二、建议修

> 下面是「不是立刻会炸、但会明显影响正确性/体验/可维护性」的问题，按优先级排列。

### S1. 个人中心：管理员入口、7 天趋势、个人统计三处都不工作
- **问题**：模板引用了不存在的 `isAdmin`、`goAdmin`、`trend`、`trendTotal`、`barHeight`；统计又用了全局 `historyCount/collectionCount` 而不是自己的 `myHistoryCount/myCollectionCount`。
- **证据**：`pages/profile/profile.vue:48`（`v-if="isAdmin"`）、`:58-71`（`trend`/`barHeight`）、`:31-33`（全局计数）；`data` 只有 `:123-134` 的字段，methods `:144-224` 没有 `goAdmin/barHeight`；后端 `app.js:177-184` 明确返回 `myHistoryCount/myCollectionCount/trend`。
- **影响**：管理员无法从 App 进后台（README 的宣传点）；趋势卡片永远不显示；登录用户看到的「识别记录/收藏」是全体用户的数字。
- **建议改法**：增加 `computed.isAdmin`（从 `userInfo.isAdmin`）、`goAdmin()`（H5 `window.open('/admin')` 或提示在浏览器打开）；`loadStats` 映射 `myHistoryCount/myCollectionCount/trend`，增加 `barHeight`；或删掉趋势模板。
- **改动量**：约 20 行、1 个文件。

### S2. 「检查更新」是死代码；深色模式/字体大小/自动保存也是摆设
- **问题**：`settings.vue` 的 `methods` 里定义了两次 `checkUpdate`，后一个（`:319-321`）只弹「当前已是最新版本」，覆盖了前面真正比对 `versionCode` 的实现（`:139-178`）。另外 `darkMode`/`fontSizeIndex`/`autoSave` 只写 storage，没有任何页面读取生效；帮助页/文档却宣称这些功能可用。
- **证据**：`pages/settings/settings.vue:139` 与 `:319`（重复 key，后者覆盖）；`:261-269`、`:307-310` 只 `setStorageSync`；全仓库搜索 `darkMode/fontSizeIndex/autoSave` 只在 `settings.vue` 出现（无消费方）；`pages/help/help.vue:24`、`docs/操作手册.md:177` 的宣传与此不符。
- **影响**：版本更新入口永远报「已是最新」；用户调了深色/字体/自动保存但毫无变化；文档信誉受损。
- **建议改法**：删掉重复的 `checkUpdate`，保留真实实现并补 `APP-PLUS` 分支；不想实现的外观设置先从 UI/帮助中移除，或至少接一个全局 class/字号变量；`autoSave=0` 时识别页不要自动写历史/本地记录。
- **改动量**：约 30 行、2~3 个文件。

### S3. 历史/收藏的删除、清空失败时仍提示成功，数据会「复活」
- **问题**：删除接口异常被空 catch 忽略，随后仍从本地列表移除并弹「删除成功」；清空收藏还逐条串行请求、全部忽略错误。
- **证据**：`pages/history/history.vue:242-248`、`:253-257`（`catch (e) { /* 忽略后端错误 */ }` 后照常改 UI）；`pages/collection/collection.vue:164-171`、`:175-182`。
- **影响**：网络失败/401 时用户以为删了，下次刷新又出现；清空收藏可能只清掉本地、服务器仍有，且 N 条请求很慢。
- **建议改法**：await 结果，失败时保留列表并 toast 原因；清空改为后端新增 `POST /api/collection/clear`（一条 SQL），不要循环调用；本地缓存只在成功后更新。
- **改动量**：约 25~35 行、2 个前端文件（+ 后端 1 个接口约 10 行）。

### S4. `invalidateBaseUrl()` 不会触发重新探测，注释与实现不符
- **问题**：网络异常时调用 `invalidateBaseUrl()` 清缓存/置标志，但 `ensureBaseUrl()` 只看 `_pending`，而它从未被清空；于是之后永远返回旧的已 resolve 地址。
- **证据**：`utils/config.js:127-131` 设置 `_probing=false; _probed=false`，但没有 `_pending=null`；`:239-247` 开头 `if (_probed && !_pending) ...`、`if (_pending) return _pending`。
- **影响**：后端 IP 变化/换 Wi-Fi 后，App 一直连旧地址，直到杀进程重启；注释宣称「下次请求重新探测」失效。这是本项目（局域网 IP 经常变）最容易踩的坑之一。
- **建议改法**：`invalidateBaseUrl()` 里加 `_pending = null`；并让 `ensureBaseUrl` 在 `_probed=false` 时重新走探测。
- **改动量**：1 行。

### S5. 监听器/摄像头未清理：内存泄漏与「离开页面还在报错」
- **问题**：`history/encyclopedia/encyclopedia-detail` 在 `onShow/onLoad` 里 `uni.$on('apiBaseUrlChanged', ...)`，从不 `$off`；`realtime` 往 `window` 加 `error/unhandledrejection` 监听，`onUnload` 只 stop 摄像头；`recognize` 的 H5 `MediaStream` 只由「取消」按钮关闭，没有 `onUnload/onHide`，且 getUserMedia 在关闭弹窗后才 resolve 时会把流挂住。
- **证据**：`pages/history/history.vue:113`、`pages/encyclopedia/encyclopedia.vue:109`、`pages/encyclopedia-detail/encyclopedia-detail.vue:159`；`pages/realtime/realtime.vue:142-150` 与 `:160`；`pages/recognize/recognize.vue:410-452`（全文件无 `onUnload/onHide`）。
- **影响**：每次进出页面叠加一个监听，多次后一次地址变化触发多次 `$forceUpdate`；离开实时监测后 window 报错仍去改已销毁组件的数据；摄像头指示灯可能一直亮，隐私/耗电。
- **建议改法**：`onUnload` 中 `uni.$off('apiBaseUrlChanged')`（用命名函数）；realtime 保存两个 listener 并在 `onUnload` remove；recognize 加 `onHide/onUnload` 调 `closeCamera()`，并在 getUserMedia 回调里判断弹窗是否已关闭。
- **改动量**：约 15~20 行、4 个文件。

### S6. 历史/百科的「下拉刷新」没有启用
- **问题**：两个页面都写了 `onPullDownRefresh`，但 `pages.json` 没有 `enablePullDownRefresh`，所以下拉动作永远不会触发。
- **证据**：`pages/history/history.vue:124`、`pages/encyclopedia/encyclopedia.vue:104` 定义了钩子；`pages.json:116-120` 的 `globalStyle` 只有颜色（无 `enablePullDownRefresh`），各 page style 也没有。
- **影响**：用户下拉无反应；代码里的 `uni.stopPullDownRefresh()` 是无效补偿。
- **建议改法**：在 `pages.json` 的 `globalStyle` 加 `"enablePullDownRefresh": true`（或分别配置两个页面），并给 `backgroundTextStyle`；不需要刷新的页面可单独关。
- **改动量**：1~3 行。

### S7. 后台复核人永远记成 `admin`（`adminUser` 拼写错误）
- **问题**：登录时 session 写的是 `adminName`，复核接口读的是 `adminUser`，于是永远回退到 `'admin'`。
- **证据**：`routes/admin.js:70` 写 `req.session.adminName`；`:636` 读 `req.session.adminUser`；全文件无 `adminUser` 赋值。
- **影响**：多条管理员时无法追溯「谁通过的纠错」；`docs/操作手册.md:345` 的「能查到是谁」不成立。
- **建议改法**：改成 `req.session.adminName`（或登录时同时写 `adminUser`），历史数据可接受。
- **改动量**：1 行。

### S8. 登录成功不清失败记录，也没有日志清理
- **问题**：`loginGuard.js` 实现了 `clearFailures` 和 `cleanOldLogs`，但全仓库没有任何调用点；成功登录不会清失败记录，登录日志表只增不减。
- **证据**：`middleware/loginGuard.js:83-90`（`clearFailures`）、`:130-132`（`cleanOldLogs`）、`:135` 导出；`controllers/user.js:89` 成功登录后只写日志；`routes/admin.js:72` 同样。`grep` 仅命中定义/导出，无调用。
- **影响**：用户偶发输错 5 次被锁 1 分钟后，正常登录也不清零；下次再错会直接升到 5/15/60 分钟档，容易误锁；`login_logs` 133 条且会持续增长。
- **建议改法**：两处登录成功分支 `await guard.clearFailures(username)`；启动时和每日/每周调用一次 `cleanOldLogs`（或加 setInterval 并 unref）。
- **改动量**：约 6~8 行、2 个文件。

### S9. 删除没有维护引用关系，已有 2 条纠错成为孤儿
- **问题**：数据库没有外键；后台删病害不清理 `collections/corrections/risk_rules`，删用户不清理 `feedback/login_logs`，删历史不清理 `corrections`。实测已有 2 条 `corrections.history_id` 指向不存在记录。
- **证据**：MySQL 只读统计：`corrections` 4 条中 2 条 `history_id` 孤儿（30、52）；`routes/admin.js:383-386`（删用户只清 histories/collections/corrections）、`controllers/history.js:71/83`（删历史不处理 corrections）、`routes/disease.js:1624`（删病害只删自己）。
- **影响**：后台纠错/审核会显示空关联；删除病害后收藏详情 404；统计口径偏差。
- **建议改法**：在删除路由里加关联清理（历史删除→corrections、病害删除→collections/risk_rules/corrections.disease_id 置空、用户删除→feedback 保留但 user_id 置空或删除）；迁移里补外键或至少定期一致性脚本。当前数据先清一次孤儿。
- **改动量**：约 15~25 行、2~3 个文件 + 1 条清理 SQL。

### S10. 分页参数没有边界校验：`page=-1` 直接后端 500
- **问题**：`page` 只做 `parseInt || 1`，负数仍会算出负 offset；MySQL 报错后接口返回 `code:500`（HTTP 仍是 200）。`pageSize` 也没有上限。
- **证据**：`routes/disease.js:107-109`（无 min/max）；`controllers/history.js:37-39`、`controllers/collection.js:26-28` 有上限但 page 同样可为负。只读实测：`GET /api/disease/diseases/list?page=-1` → `{"code":500,"data":{"list":[],"total":0},"msg":"服务器异常"}`；`pageSize=100000` → 返回全部字段（20,287 字节，19 条）。
- **影响**：边界输入导致 500；`pageSize` 放大可一次拖全表（未来 249 条 verified 时更明显），无意义带宽/内存。
- **建议改法**：统一 `page = Math.max(1, ...)`、`pageSize = Math.min(100, Math.max(1, ...))`；非法参数返回 400；错误响应改 HTTP 4xx/5xx，不要一律 200。
- **改动量**：约 10 行、3 个文件。

### S11. Session 用 MemoryStore、cookie 未加 `secure/sameSite`，后台无 CSRF token
- **问题**：`express-session` 默认 MemoryStore，重启即掉登录且不适合生产；cookie 只有 `httpOnly`；后台表单没有 CSRF token（`csurf` 在 package.json 但从未 require）；`/admin/logout` 是 GET。
- **证据**：`app.js:97-102`（没有 `store`，cookie 只有 `maxAge/httpOnly`）；`package.json:15`（`csurf` 未使用）；`routes/admin.js:139`（GET logout）。
- **影响**：PM2 重启后管理员需重新登录（可接受但不专业）；HTTPS 下 cookie 仍可能走 HTTP；CSRF 主要靠浏览器默认 SameSite=Lax，用显式 token 更稳。
- **建议改法**：生产用 `connect-sqlite3`/MySQL store（或至少接受重启掉线并在文档说明）；cookie 加 `sameSite:'lax', secure: NODE_ENV==='production'`；后台表单加 CSRF token 或校验 Origin/Referer；logout 改 POST。
- **改动量**：约 15~25 行、1~2 个文件 + 依赖（若上 store）。

### S12. 识别会使用未核实草稿，且每次识别全表 `SELECT *`
- **问题**：`matchLocalDisease` 明确查全库（含 230 条 verified=0 草稿），匹配后直接用草稿的症状/用药作为 App 结果；而百科接口只返回 verified=1，规则不一致。每次识别都 `SELECT * FROM diseases`（包含全部 MEDIUMTEXT）。
- **证据**：`routes/disease.js:347-363`（注释写明「不能只查 verified=1」）、`:952`（`mergeWithLocal` 使用 local）；识别主流程 `:940-941` 调用它；列表接口 `:113` 却过滤 `verified=1`。
- **影响**：App 里看不到的草稿内容会出现在识别结果中（内容质量/合规风险）；249 条 × 大字段的查询在实时监测 24 次/分下是明显浪费。
- **建议改法**：明确产品策略——若坚持 verified-only，匹配时加 `verified=1`（或用草稿只做名称去重，不回填正文）；缓存 `id,name,verified` 的轻量列表（启动/变更时刷新），不要把 `SELECT *` 放在每帧热路径。
- **改动量**：约 10~20 行、1 个文件。

### S13. `/api/history/add` 接受任意 `image_url`，可伪造图片归属
- **问题**：登录用户可把 `imageUrl` 设成任意字符串（包括别人的 `/uploads/...`）；`/uploads` 的归属判断正是按 `histories.image/image_url LIKE` 放行，因此可给自己「授权」一张别人的图（只要知道文件名）。
- **证据**：`controllers/history.js:10-11`（`imageUrl || req.body.image` 直接入库）；`app.js:297-302`（按 `user_id + image LIKE` 放行）。
- **影响**：配合文件名泄露（日志/分享）可越权读图；也会制造数据库里指向他人文件的记录。
- **建议改法**：`addHistory` 只接受 `/uploads/<本用户上传过的文件>` 或服务端识别返回的路径（最好由服务端签发/校验）；对 `image_url` 做正则 + 存在性 + 归属校验；或干脆不信任客户端，改由识别接口写历史。
- **改动量**：约 8~12 行、1 个文件。

### S14. 每张图访问要做 3~4 次数据库查询，没有缓存
- **问题**：`/uploads` 路由为了判断归属，依次查 `diseases`、`users.avatar`、`histories` 三次（管理员还多一次 `users.is_admin`）；列表页一次加载十几张图就是几十次查询。
- **证据**：`app.js:278-301`；前端百科/历史/收藏每张图都带 token 走该路由（`utils/config.js:142-170`）。
- **影响**：图片加载延迟；MySQL 压力随图片数线性增长；缓存命中也没有。
- **建议改法**：用一次 `SELECT ... UNION ALL` 或内存 LRU（文件→归属，TTL 5 分钟）；已核实病害图/头像可走公开缓存；对 `sendFile` 设置 `Cache-Control`。
- **改动量**：约 20~30 行、1 个文件。

### S15. 文档与接口/代码不一致（含安全承诺）
- **问题**：`接口文档.md:31` 写识别「限流 8 次/分钟」，代码是 60（`routes/disease.js:733`）；`:12` 把 `/uploads/*` 写成静态图片，实际需要登录（`app.js:256`）；`开发文档.md:806` 称 JWT 仍硬编码 4 个文件（实际已集中到 `config/secrets.js`）；`操作手册.md:345` 称复核可查操作人（实际见 S7）；`操作手册.md:177` 检查更新（实际见 S2）。
- **影响**：联调/验收按文档测试会误判；安全承诺与实际不符，答辩/上线时容易被问住。
- **建议改法**：以代码为准更新接口文档的鉴权、限流、上传说明；文档里加「最后核对 commit」；对「检查更新/复核人/设置项」要么修代码要么删承诺。
- **改动量**：约 10~20 行文档。

### S16. 后台 HTML 有嵌套 form、样式残缺和调试 UI
- **问题**：`diseases.ejs` 外层批量核实 `<form>` 内又嵌了每行的核实/补图/删除 `<form>`，HTML 不允许嵌套；`settings.vue:353` 有一行孤立的 ` scoped>` 破坏 CSS；`realtime.vue:92` 把 `v4 · 点击 N 次 · 状态` 调试信息显示给用户；`realtime.vue:277-283` 同一段状态赋值写了两遍。
- **证据**：`views/admin/diseases.ejs:51` 与 `:98-118`（内层 form）、`:125`（外层闭合）；`settings.vue:353`；`realtime.vue:92`、`:277-283`。
- **影响**：不同浏览器对嵌套 form 的提交目标处理不一致，行内「核实/删除/补图」有失效风险；设置页部分样式可能整块失效；调试文字降低产品感。
- **建议改法**：批量操作表单只包 checkbox（用 `form` 属性把按钮关联到独立表单，或每行独立 form 不嵌套）；修正 `<style scoped>`；删调试行/版本号。
- **改动量**：约 20 行、3 个文件。

### S17. 收藏无分页、百科固定 50 条且搜索只搜已加载数据
- **问题**：收藏页只拉默认 50 条且没有「加载更多」；百科一次 `pageSize=50`，搜索在前端过滤这 50 条，不请求服务端 `keyword`。现在 verified 只有 19 条，所以问题被数据量掩盖。
- **证据**：`utils/api.js:213`（`getCollectList()` 无参）；`controllers/collection.js:27`（默认 50）；`pages/encyclopedia/encyclopedia.vue:118`（固定 50）、`:152-158`（本地 filter）；后端已支持 `keyword`（`routes/disease.js:110-118`）。
- **影响**：收藏超过 50 条后永远看不到；百科数据增长到 50+ 后搜索会漏结果，用户会以为库里没有。
- **建议改法**：收藏页加 `page/pageSize` + 上拉加载；百科改为「输入防抖后请求服务端 keyword」，或至少分页加载全部后再本地过滤。
- **改动量**：约 25~35 行、2 个前端文件（+ 无需后端改动）。

### S18. 分享链接对历史记录会带错 id；时间线分享 id 为空
- **问题**：`diseaseId` 从未定义，`onShareTimeline` 的 `query` 为空；从历史记录打开详情分享时，`d.id` 是历史记录 id（不是病害 id），分享出去会打开错误的病害。
- **证据**：`pages/encyclopedia-detail/encyclopedia-detail.vue:238`（`this.diseaseId || d.id`）、`:251`、`:268`；`loadFromHistory` 在 `:349-371` 把历史 id 赋给 `disease.id`。
- **影响**：用户转发历史结果，对方打开的是另一条病害；时间线分享缺 id 直接加载失败。
- **建议改法**：增加 `computed diseaseId`（只在非 history 时返回 `disease.id`）；history 记录不提供百科分享，或分享时带 `hid`；`onShareTimeline` 用 `this.diseaseId`。
- **改动量**：约 8~12 行、1 个文件。

### S19. `mergeWithLocal` 会被本地空数组挡住，AI 的用药建议丢失
- **问题**：本地记录字段是字符串 `'[]'`（truthy），`arr('[]')` 返回空数组且没有 fallback，于是 AI 返回的 `medicines/suggestions/prevention` 不会补上。
- **证据**：`routes/disease.js:481-483`（`d.medicines ? arr(d.medicines) : arr(picked.medicines)`）；`arr()` 在 `:457-461`。
- **影响**：识别结果可能显示「无推荐用药/无防治建议」，即使 AI 已经给出；用户会误以为该病无药可治。
- **建议改法**：判空后再决定：`const localList = arr(d.medicines); medicines: localList.length ? localList : arr(picked.medicines)`。
- **改动量**：3 行。

### S20. 同名函数重复定义，病害名匹配逻辑被后者覆盖
- **问题**：`normalizeDiseaseName` 在 317 行与 428 行各定义一次；后者的「空词过滤」覆盖了前者的「去掉寄主前缀/括号/结尾病字」，导致 `nameScore('玉米大斑病','大斑病')` 不再走包含关系，容易匹配失败并重复收录。
- **证据**：`routes/disease.js:317-322` 与 `:428-432`；`nameScore` `:331-344` 使用它；`autoLearnDisease` `:396-399` 用它去重。
- **影响**：AI 识别结果与本地库匹配率下降，同一病害可能被重复收录；注释与实现不符。
- **建议改法**：合并成一个函数（先清空词再 normalize 前缀），或把第二个改名为 `emptyDiseaseName` 并显式调用。
- **改动量**：5~8 行、1 个文件。

## 三、可以不改

> 这些是「看到了，但按当前项目体量/风险不值得专门排期」的点；如果顺手改也可以。

1. **未使用的依赖**：`body-parser`、`cookie-parser`、`csurf`、`sql.js` 在运行代码中未 `require`（`package.json:12-15`）。删掉可减依赖面；但 `csurf` 如果不用应删除，避免误以为已做 CSRF。
2. **重复索引**：MySQL 上 `histories` 同时有 `idx_histories_user` 与 `idx_histories_user_time`（同列），`diseases` 同时有 `idx_diseases_name` 与唯一索引 `name`。浪费一点写入性能，当前数据量可忽略。
3. **死代码/遗留**：`controllers/disease.js` 两个函数没有路由引用；`routes/disease.js:303` 的 `s.replace(/" + BT3 + "(?:json)?/gi, '')` 是无效正则（真正靠首尾花括号提取 JSON，功能不坏）；`db.js` 的清理函数只对 SQLite 生效。
4. **仓库中的构建产物**：`dist/`（17.5 MB，含 15 MB APK）被 git 跟踪且可能落后于源码；`start-all.ps1` 在没有 HBuilderX 时会直接用它。建议发版时重建，平时从仓库移除（`.gitignore` 只忽略了 `unpackage/`）。
5. **登录/注册对密码做了 `.trim()`**：`pages/login/login.vue:78`、`register.vue:117` 会把首尾空格去掉；用户若真的用带空格密码注册，前后端行为不一致。当前注册/登录都 trim，影响很小。
6. **健康检查泄露数据库错误文本**：`app.js:152` 把 `e.message` 原样返回给公网；MySQL 连接失败时会暴露主机/端口。可改为统一「数据库异常」并只写日志。
7. **压缩中间件会整段缓冲图片**：`middleware/production.js:39-69` 先收集所有 chunk，再判断 `skipType`；图片虽不压缩，但仍会整张进内存。5 MB 上限下可接受。
8. **SQLite 旧副本与 MySQL 分叉**：`agriculture.db` 没有 `schema_version`/`risk_rules`，与当前 MySQL 数据不同（27 vs 19 verified）。目前 `.env` 是 MySQL，旧文件不影响运行；但不要拿它当备份。
9. **`backfillDiseaseCategories()` 的 SQL 条件**：`db.js:684` 会把 `category` 不等于该类型的已知 type 覆盖为类型名（注释说保留 AI/人工标记，实际会覆盖）。当前数据没有命中，将来可能有。
10. **`cleanupJunkDiseases`/`cleanupDuplicateHistories` 的启动清理**：前者会删长度 >12 的病害名（仅 SQLite 启动时），后者按 `disease_name,image_url,create_time` 去重但没带 `user_id`（跨用户可能误删）。当前没有触发数据，但不要依赖它们做数据治理。
11. **告警「最新」标记不重置**：`warnings.is_new` 只在种子数据写 1，没有代码归零；列表会一直显示「最新」。纯展示问题。

> 以上各项单项改动量均 < 0.5 天、多数 < 30 行；不建议为此单独立项，随相关功能一起顺手处理即可。
